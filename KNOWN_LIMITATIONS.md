# Известные ограничения и непроверенное

## Не реализовано в этом релизе
- `Pitachok Loader.exe` (WPF), UI админ-панели, готовый бинарник `HudLoader.asi` (исходники есть, но не собирались), `hud.asi`. В среде сборки нет .NET SDK и Windows-тулчейна.
- Backend сделан на Node + SQLite (не ASP.NET Core + PostgreSQL, как рекомендовал мастер-промпт), потому что только его можно было собрать и протестировать здесь. Для нагрузки сотен разработчиков одного узла SQLite достаточно; миграция на PostgreSQL потребует правки `db.js`.

## Backend: что не проверено
- Реальная публикация в GitHub: клиент проверен только на имитации API (сети в среде нет). Нужна проверка на вашем репозитории и токене.
- HTTPS не терминируется самим сервером — нужен reverse proxy. Rate limit хранится в памяти процесса (один экземпляр).
- Генерация hud.js синхронна и блокирует цикл событий на ~сотни мс; при высокой нагрузке вынести в worker.
- Нет автоматической ротации ключа подписи и списка отозванных ключей (поле `keyId` подготовлено).
- Резервное копирование и восстановление описаны, но не автоматизированы.

## Шаблон hud.js — что поддерживается
Применяется: auth, 12 иконок, оружие, 21 логотип, форма радара, толщина и цвет обводки, цвет «окон» (applyInterfaceColor).
НЕ применяется (в шаблоне нет кода/ресурсов; генератор выводит предупреждение): цвет чата, HP/Armor/Food,
табло капта, кастомные диалоги.
- Оружие: в шаблоне ID 0–44 и 46; 45, 47, 48 отсутствуют.
- Толщина обводки — в `vh` (было захардкожено 0.60vh). Цвет обводки по умолчанию в шаблоне `#F000` (прозрачный).
- Цвет окон применяется при загрузке; поведение в игре не проверено.

## Проблемы существующего шаблона (не исправлены автоматически)
- Проверка статуса (`checkHudStatus`) всегда пропускается: `HUD_HWID` равен строке, с которой сравнивается, так что удалённое
  отключение внутри JS не работает; при ошибке сети — fail-open; остались отладочные `alert(...)`.
  Отзыв доступа должен делать backend/loader, а не этот JS.

## Не проверялось
- Работа результата в Radmir/GTA SA/CEF и совместимость с Temida: целевой среды нет.
- Способ загрузки hud.js внутри `hud.asi` (бинарник упакован, исходников нет).
- Исправление AUTH-фона при реконнекте проверено только на синтаксис, не в игре.

## Защита платных HUD: границы возможного
- Серверная часть (ключ на покупателя, привязка к устройству, отзыв, пометка ключей) реализована и протестирована.
- Исполнять решение на ПК игрока должен loader (`.asi`), которого пока нет. Любая защита, работающая на компьютере пользователя, обходится
  достаточно умелым человеком (например, отключением проверки или копией уже выданного `hud.js`). Реальный эффект даёт отзыв ключа + короткий срок
  лицензии + закрытая загрузка; отзыв не удалит файл, уже лежащий на диске, а лишь не даст официальному loader его запускать.
- Не реализован водяной знак на каждого покупателя (уникальная метка в сборке для поиска источника утечки) — можно добавить следующим шагом.
- HWID собирает loader: об этом нужно сообщать покупателям (персональные данные), сервер хранит только необратимый HMAC.
- Чужие защищённые загрузчики (`ModsLoader_1.asi` и др.) не разбирались и не копировались.

## Loader (HudLoader.asi / .build)
- Ядро проверки подписей (C) протестировано; `loader/win/hudloader_win.c` написан, но не компилировался и не запускался. Вероятны мелкие
  правки при первой сборке MinGW (например, сигнатура `swprintf`).
- Как скрипт попадает в клиент игры, не реализовано: loader отдаёт проверенный `hud.js` через экспорт `HudLoader_GetScript()`, а принять его
  должен `hud.asi`/другой модуль. Я не знаю интерфейса вашего `hud.asi` и не буду обходить защиту игры или античита.
- Кэша на диске нет: `hud.js` (с картинками) живёт только в памяти процесса игры. Следствие: после перезапуска игры нужна сеть; без сети уже запущенный HUD работает до `expiresAt` лицензии (по умолчанию 72 ч).
- Время для проверки срока берётся из системных часов ПК: игрок может перевести часы назад и продлить офлайн-режим. Закрывается только
  онлайн-проверкой (при работающей сети срок обновляется сервером каждые 30 минут).
- `.build` содержит ключ покупателя: его утечка = утечка лицензии, но она привязана к устройствам и отзывается (`revoke` / `rotate-key`).

## Панель и билдер
- Панель — веб-страница, а не отдельное десктоп-приложение; открывается в браузере по адресу сервера. Доступ только по логину и паролю владельца или разработчика.
- Метка ПК в панели — `PC-` + 12 символов необратимого хеша устройства; имя компьютера loader не отправляет (это персональные данные). Узнать «чей» ПК по метке
  можно, сопоставив время первой активации с моментом, когда вы отправили ключ покупателю.
- Окно WPF-билдера не сделано: выбор «платный/бесплатный» сейчас доступен через CLI (`--type`) и поле `distribution` в конфиге.
- Панель держит токены только в памяти страницы: после обновления страницы нужно войти заново.

## Где лежит hud.js и что видит покупатель
- У покупателя на диске: `HudLoader.asi`, `HudLoader.build` (ID HUD, адрес сервера, его ключ), `HudLoader.log`. Картинок и `hud.js` там нет.
- На билдере: команда `publish` отправляет конфиг и картинки на сервер, `hud.js` генерирует сервер; локально `hud.js` не создаётся (команда `build` — только для ручной сборки).
- На сервере `hud.js` хранится в `server/data/artifacts` (рабочая копия) и зеркалируется в приватный GitHub-репозиторий. Платный HUD сервер откажется
  публиковать в публичный репозиторий (проверка `private` через API GitHub).
- Покупатель получает `hud.js` только через ваш сервер, пока ключ действует и ПК привязан; напрямую с GitHub loader не качает (иначе в клиенте пришлось бы хранить токен).
- Пока HUD запущен, картинки есть в памяти игры и на экране: скриншот или дамп памяти запретить нельзя.
